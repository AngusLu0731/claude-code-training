## 用途

一個 Claude Code session 就是一個 context、一個工作目錄。你把兩件不相干的事塞進同一個 session，它們會互相污染：前一件事的檔案、討論、決定全都留在 context 裡，第二件事的品質跟著下滑，而且兩件事都得排隊等對方。
多 session 多工就是把「一件事」對應「一個 session」，讓它們**同時**進行。難點不在開很多視窗，而在**不要互相踩檔**：兩個 session 在同一個 checkout 改同一批檔案，結果就是 diff 互相覆蓋。
`claude --worktree` 用 git worktree 幫每個 session 開一份獨立的工作目錄與分支，各做各的，最後由你在主 checkout 把成果 merge 回來——這一章就在練這件事。

## 什麼時候用

### 情境 A：兩件互不相干的任務

要加一個 CLI 選項、同時要補 README 的使用範例。兩件事碰的檔案完全不重疊，一個 session 做完再做另一個純粹是在排隊。開兩個 worktree session，各自派一件，時間直接砍半。

### 情境 B：一邊跑長任務、一邊改別的

一個 session 正在跑一個要十幾分鐘的重構或測試修復，你不想在旁邊乾等。開第二個 worktree session 處理另一件小事，長任務那邊不會被你的新提示詞打斷，也不會看到你正在改的檔。

### 情境 C：一個 session 看 log、一個改 code

排查問題時，一個 session 專門讀 log、整理線索、給你結論；另一個 session 拿著結論改 code。兩邊的 context 各自乾淨：讀 log 的那個不會被程式碼的討論淹沒，改 code 的那個也不用背著幾萬 token 的 log。

### 反例：同一個 checkout 開兩個 session 改同一批檔

在**同一個目錄**開兩個 `claude`，各自要求改 `src/todo.py`。兩個 session 看到的是同一份檔案，A 剛寫進去的內容 B 下一秒就覆蓋掉，`git status` 也分不出誰改了什麼。這不是多工，是互相破壞。真的要動同一批檔，就排隊，或先拆成不重疊的工作。

## 基本用法

### 開一個 worktree session

```bash
claude --worktree <name>
```

Claude Code 會在 repo 根目錄下建 `.claude/worktrees/<name>/`（一份獨立的工作目錄），並開一條新分支 `worktree-<name>`，然後在那個目錄裡啟動 session。`-w` 是同一件事的縮寫。
同名再開一次，會直接進既有的 worktree。它預設從 repo 的預設分支（通常是 `main`）長出來，所以每個 worktree 的起點都是乾淨的。

### 一個 session 一件事

給每個 session 的提示詞要**自足**：做什麼、只准碰哪些檔、做完要 commit 還是不要。session 之間看不到彼此的對話，所以「不要動 README」這種邊界一定要寫進提示詞，不能靠它自己猜。

### 收斂：摘要＋回主 checkout merge

每個 session 收尾時請它用一句話摘要做了什麼、commit 了哪些檔。然後你回**主 checkout**（不是任何一個 worktree）做 merge：

```bash
git merge --no-ff worktree-a
git merge --no-ff worktree-b
```

`--no-ff` 讓每個 session 的成果在 `git log --graph` 上各自成一個 merge 節點，事後看得出來哪批改動來自誰。

### `/exit` 時的 keep／remove

在 worktree session 打 `/exit`，如果裡面有改動，Claude Code 會問要 **keep** 還是 **remove**：

- **keep**：保留目錄與分支，之後 `claude --worktree <同名>` 可以回來繼續。
- **remove**：刪掉目錄與分支，**裡面沒 merge 出去的改動一起消失**。

規則很簡單：已經 merge 回主 checkout 的選 remove；還沒的選 keep。

### 團隊真實案例（去機密版）

一個團隊的後端開發流程被寫成一條五站的 workflow：**ROUTE → SPEC → BUILD → VERIFY → DONE**，SPEC 站硬停等人確認才往下走。這種長流程一跑就是幾十分鐘，工程師的做法是：主 checkout 留給自己看 diff 與回答 SPEC 站的問題，另外開一個 `--worktree` session 處理不相干的小修——長流程不受打擾，小修也不用等。

## 你來做

<Exercise id="ch1-ex1" title="兩個 worktree 分工，第三個終端機收斂">

這一章的起點是 clone。之後各章都用「重置」把 repo 拉回乾淨的 `main`。

<Steps>

0. **起點**：clone 練習 repo（已經 clone 過就跳過，直接 `cd` 進去）。

   ```bash
   git clone https://github.com/AngusLu0731/claude-code-practice.git
   cd claude-code-practice
   ```

1. **步驟 0.5**：第一次在這個目錄開 `claude`，接受信任對話後 `/exit`。已經做過就跳過。

   ```bash
   claude
   ```

2. **終端機 A**：開 worktree `a`，整段貼這個提示詞。

   ```bash
   claude --worktree a
   ```

   ```text
   只改 src/todo.py 與 tests/test_todo.py：list 加 --json 輸出（印出 JSON 陣列，每筆含 text 與 done）並補測試，不要動 README，做完只 commit 不要 push
   ```

3. **終端機 B**：再開一個終端機，`cd` 到同一個 repo，開 worktree `b`，整段貼這個提示詞。

   ```bash
   claude --worktree b
   ```

   ```text
   只改 README.md 加三個使用範例，不要動 src/ 與 tests/，做完只 commit 不要 push
   ```

4. **終端機 C（主 checkout）**：等 A、B 都回報「已 commit」，再開第三個終端機，在 repo 根目錄（不是 `.claude/worktrees/` 底下）收斂：

   ```bash
   git merge --no-ff worktree-a && git merge --no-ff worktree-b && python3 -m unittest -v
   ```

5. 回終端機 A、B 各打 `/exit`。它會問 keep／remove，選 **remove**——成果已經 merge 進 `main`，刪掉是安全的。

6. 在主 checkout 清掉殘留的 worktree 記錄與分支：

   ```bash
   git worktree prune && git branch -d worktree-a worktree-b
   ```

</Steps>

### 預期看到

- 步驟 4 的 merge 沒有衝突；`python3 -m unittest -v` 最後幾行是 `Ran 14 tests`（或更多——`main` 本來有 13 個，A 每補一個測試就加一）與 `OK`。
- `git log --oneline --graph` 最上面有**兩個 merge 節點**（`Merge branch 'worktree-a'`、`Merge branch 'worktree-b'`）。
- `python3 src/todo.py list --json` 印出 JSON（空清單就是 `[]`）。
- 步驟 6 之後 `git worktree list` 只剩主 checkout一行，`git branch` 沒有 `worktree-a`、`worktree-b`。

### 故障排除

- **merge 衝突**：`git merge --abort`，回那個 session 說「只改指定檔案，重做一次」，它多半是動到了不該動的檔。
- **remove 顯示 locked**：`git worktree unlock .claude/worktrees/<name>` 再 remove 一次。
- **B 動了 src/**：提示詞邊界沒寫清楚，這是本章要你學到的事——把「不要動 src/ 與 tests/」寫進去再來一次。
